## 0.23.13 · 知弦

### 接口自述与真实能力对齐

- `internal/capabilities` 不再列 `like`：0.23.0 起资料卡点赞随着「只走 JNI 层」一起没了，但能力表里还留着，
  客户端照着调只会拿到 404 再白试一轮。现在单独给一段 `removed`，逐项写明「哪个版本、为什么」。
- 曾经有过、后来移除的动作（0.17.0 的内核查询、0.23.0 的 `like`）报错时与「方法名写错」分开：
  404 的响应体里带 `code=removed_action`，客户端按机器可读的字段判断，不必匹配会变的中文文案。

### 骰子与猜拳改成超级表情（按 NapCat 的实现对齐）

之前发的是 `FaceElement.faceType=1`，群里收到的是一个 16px 的小脸。对照
[NapCat](https://github.com/NapNeko/NapCatQQ) 的实现改对，要点有两处：

- `FaceType` 的取值是 `1 老表情 / 2 常规表情 / **3 动画贴纸 = 超级表情** / 4 Lottie / 5 poke`
  （`packages/napcat-core/types/msg.ts`）。先前猜的 2 是「常规表情」，所以还是小脸。
- 光有 `faceType=3` 不够，还要带贴纸身份：`faceText`（`[骰子]` / `[包剪锤]`）、`packId='1'`、
  `stickerId`（骰子 `33`、猜拳 `34`）、`stickerType=2`、`sourceType=1`；线路上 QQ 会把它编成
  `commonElem{serviceType:37}` 里的一段 `QBigFaceExtra`（`aniStickerPackId` / `aniStickerId` /
  `faceId` / `sourceType` / `resultId` / `preview` / `randomType`），但那是内核自己做的转换，
  交给内核的仍然是 `FaceElement`，照着 NapCat 的 dice / rps 段填即可。

顺带把普通表情的 `faceType` 也按同一份实现的选法补齐：id ≥ 222 用 2，小于 222 用 1。
先前一律发 1，id 大于 222 的表情在 QQ 里是画不出来的。

### 群名变空：最可能是平台侧处置，守卫改成默认只观察

2026-09-19 追了一整天的「测试群名变空」有了最站得住的解释：**不是实现端写的**。审计日志里没有
任何写入记录，而当天对这个群的群设置写入极其频繁——改名先后被 `code=1010` 拒过一次（隔十几秒
重试就成功，是改名频率限制），成员禁言与上下管理也多次撞上 `code=120101154`。名字被清掉、
重启后仍是空的、又抓不到本地写入，这三件事合起来指向平台侧的处置。

于是名字守卫改成**默认只观察**：发现名字为空先做一次全量刷新（区分本地缓存空与真空），刷新后
仍为空就只记一行 `name_guard=empty:<群>(见过=<名字>)`，**不写**。要自动写回得显式打开
`restore_empty_group_name`（管理页新开关），打开后每小时最多恢复 2 次。

同时把巡检里两个名字带 `read` 但其实会写群设置的用例（`internal/title_display` /
`internal/honor_display`）改成默认不跑——别再把写操作往同一个群上堆。

### 群名守卫：变空先刷新，仍为空就写回来（原始设计）

测试群的名字反复变空，而 `satori-writes.log` 里**没有任何写入记录**——不是改名路径干的，逐个
探测每个 `internal/*` 动作、成员禁言、上下管理、改名往返也都复现不出来。既然一时抓不到是谁，
先让症状自愈并且**可归因**：

- **名字守卫**（每两分钟一次，仅对「我们见过名字」的群）：发现名字为空先用全量刷新区分
  「本地缓存空」与「真的空」——刷新就回来的一个字都不写；刷新后还是空，就用见过的那个名字写回去。
  每小时最多恢复 2 次，真有未知的清除者在拉锯，日志里看得见，也不会变成无限改名。
  `GET /healthz` 的 `name_guard` 字段记着最近一次结论（`refresh-back:` / `restored:` / `budget-used:`）。
- 见过的名字**落盘**（`files/satori-group-names.tsv`，一百来个群，改动时整体重写、每分钟最多一次），
  否则「重启之后名字是空的」这种情形守卫会失忆——用户两次都是在重启后发现的。
- 群名的每次写入本来就有审计；这次把**测试群名变空到底是谁干的**这件事交给审计日志去回答，
  下次再发生，`satori-writes.log` 里会有那一行。

### 刚清掉的表情不再被本地兜底读回来

`reaction.list` 在内核实时查询没结果时会退到本地记录，而那段兜底的优先级写反了：本地记账说
「我们取消过」，代码却去看内核记录里滞后一拍的 `isClicked`，于是 `reaction.clear` 之后立刻回读
会回 1 个人（就是我们自己），看起来像没清掉（2026-09-19 逐步手工复现确认）。现在本地记账优先，
只有模块重启过、没有记账时才退到内核记录的 `isClicked`。顺带把写操作巡检里那两处读回改成轮询
（服务端自己有一两秒的可见性延迟，不是实现端读错）。

### 常驻与抗冻：不用 hook 也要留住进程

0.22.x 及更早是靠 hook 把 QQ 的服务提成前台服务来保活，去掉 hook 引擎后那条路没了。这一版补上
不 hook 也能做的那一半，并把兜底挪到 root 侧：

- **模块**：会话就绪后每十分钟把自己（QQ）的服务重新 `start` 一遍。本机实测 app freezer 的判据是
  `oom_score_adj ≥ 900`，QQ 主进程在有已启动服务时是 ~700，冻不着；服务全停才掉进可冻结区间。
  `/healthz` 与 `internal/status` 新增 `keepalive` 字段（`adj` / `wchan` / `service`），抗冻到底有没有
  生效一眼能看到。
- **看守**（`scripts/qq-revive.sh`）：解冻从「`monkey` 拉到前台」改成**写进程自己的 freezer cgroup**
  （AOSP 按进程冻、ColorOS 按 uid 冻，两处都写 0），不打断用户、不重新登录、不消耗重启预算。
- **手动停掉 QQ 就不再拉起**：判据是包状态的 `stopped=true`（「强行停止」置位，系统自己杀进程不会）。
  实测：强停后看守只记一行 `skip: ... 用户手动停掉了 QQ（stopped=true），不拉起`，QQ 保持关闭；
  手动启回来时标志自动清零，模块照常上线。

移动数据侧补了说明：`wifi_sustain` 只在 Wi-Fi 下有意义（`WifiLock` 对蜂窝无效），蜂窝下靠的是
进程不被冻/不被杀与后台数据没被限制。App 里那条设置的提示也改成了实话。

### 群名「变空」的真正原因：增量更新把已知的名字覆盖掉了

测试群的名字两次「变空」，一开始都归到「有谁把它写空了」。加了 `satori-writes.log` 之后定性：
日志里**一条写入记录都没有**，所以不是写坏的。真正的原因在群列表的增量更新——QQ 推来的
`GroupSimpleInfo` 只带变化了的字段，没变化的名字是空的，而实现端直接 `put` 覆盖了缓存，
于是这个活跃的群在一段时间后就没有名字了，直到下一次全量刷新才回来。现在增量更新按**合并**
处理：新值非空用新值，旧的非空值留住。

（附带修掉的）：

**实现端**：`setGroupName` 拒绝空名字（连内核都不发），`modifyGroupDetailInfoV2` 这条兜底在发之前
先读回 `GroupModifyInfo.groupName` 确认值真的写进去了——这条路径是唯一一处「按字段名写入」，字段名
对不上时 `put` 会静默失败，然后带着一个空的 groupName 发出去就是清空群名。另加 `satori-writes.log`
（QQ 私有目录）把每次群名／群头像写入的值与内核回执记一行：这类事故事后只能靠这一行定性，logcat
主缓冲几秒就被 QQ 刷掉了。

**测试**：改名与全员禁言改成**默认不跑**，要跑得显式给 `SATORI_DESTRUCTIVE=1`。群名对外可见、
清掉补不回来，不该是回归测试的默认副作用。顺带把 `internal/poke` 的用例改成戳别人——服务端对
「戳自己」回 `Process_Nudge failed`，那不是协议问题。

### 参数错的请求不再打开出站熔断

出站熔断的判据是「内核是不是在拒绝干活」，但 1400/1404（调用方参数不对）也被算了进去：那是
实现端进内核之前自己回绝的，跟内核无关。后果是任何客户端**连发三个缺参请求**就能把出站通道锁
`circuit_open_ms`（默认两分钟），期间连正常发送也被拒（实测：巡检里的缺参用例正好触发，后面
十几项全挂）。现在 1400/1404 与从未实现的方法（404）都不计进熔断。

### 群名：一段追错了方向的兜底，已收掉

0.23.2/0.23.3 加过一层「内核 simple-info 没名字就去要群详情」的兜底（最后自己写了三个内核
接口的调用）。事后查明那个空名字是**测试自己改坏的**——`ws-write-sweep` 的改名用例把原名读成
空串，还原时写回空串，群里就留下一个没名字的群。兜底本身没有存在的理由，已收回，只保留
「`groupName` 空了退 `remarkName`」这一行。

真正的修复在测试侧：改名用例现在两个来源都读一遍原名、读到空串就不改名、**还原放进 `finally`**、
读回带重试，还原后读不到原名会明确报错要人工确认。

### 入站计数

`internal/status` 新增 `inbound`：`recv` / `add` / `update` / `gray_tip` / `emitted` /
`notices` / `manual_self`。事件收不到时先看这几个——能分开「记录压根没进来」「进来了但没转成
事件」「转了但客户端没消费」三种情况。
