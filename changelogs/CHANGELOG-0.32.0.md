# 0.32.0 — 资源只走 internal: 链接，上传不进堆

对着官方资源文档过了一遍：协议明确把「由 SDK 自己提供一条访问资源的路由、再把链接换成指向它的 URL」
列为不推荐的做法，理由是链接与服务器地址耦合、本机再请求自己。这一版把它改掉，顺带处理上传的内存问题。

- **收到的媒体是 `internal:red/{uin}/_tmp/{id}`**：之前是 `http://127.0.0.1:3001/v1/assets/…`，
  把监听地址写进了每条消息（绑 `0.0.0.0` 时甚至是 `http://0.0.0.0:3001/…`）。现在链接不带地址，
  客户端经 `/v1/proxy/{url}` 读取；原样放进回复里时本端直接从磁盘解析，不再请求自己。
  `/v1/assets/{id}` 路由与 `chat_screenshot` 返回里的 `url` 一并删除，只剩 `internal:`。
- **`upload.create` 流式落盘**：原来整份请求体读进堆再复制一次，63 MiB 的视频要占 QQ 进程约 130 MiB，
  撞上 OOM 时异常被吞掉、连接直接断开，客户端只看到「发送失败」。现在 multipart 边读边写文件，
  堆里只有一个 128 KiB 窗口（`-Xmx64m` 下传 60 MB 仍成功）。
- **超限先答后断**：声明的请求体超过上限时，先回 413 并把客户端还在发的部分丢掉再关连接。
  之前直接关，客户端收到的是 RST，读不到那条 413（acumen 日志里的 `error sending request`）。
  `Expect: 100-continue` 也认了。
- **`/v1/proxy` 按块回包并支持 `Range`**：不再整份读进堆；`bytes=a-b` / `a-` / `-n` 回 206，越界 416。
- **`user.nick` 不再是群名片**：`user` 描述这个人，`name` 与 `nick` 都是 QQ 昵称；群名片归成员，在
  `member.nick`。之前同一个账号在不同群里的 `user.nick` 不一样。
- **心跳超时先发关闭帧**：冻结后才醒来的客户端读到的是关闭帧而不是连接重置，带 `sn` 重连即可。

验证：JVM 测试新增流式 multipart（任意读块大小、边界跨读、超限与残缺）、真套接字的流式路由、
提前 413、`Expect: 100-continue`、`Range` 与 `internal:` 媒体链接；共享探针 `conformance.py` 要求
`Range` 回 206/416，并检查事件里的媒体不带本机地址。改动在 Java 层，代码内嵌在 Zygisk 的 `.so` 里、
开机时钉住：装机要覆盖模块文件后**重启手机**才生效。
