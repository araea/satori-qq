# 0.32.2 — 禁言通知读不出时长时不再编一个 1 秒

给群里的禁言排行榜（acumen 的 stats）做数据时发现的：真机缓冲里别人被禁言的两条通知，
`duration` 都是 1000 毫秒、也没有操作者。普通群友看到的禁言灰条读不出时长时，
`parseBanDuration` 兜底返回了 `1`——下游分不清「禁言 1 秒」和「没读出来」。

- **读不出就说读不出**：`Notices.UNKNOWN_DURATION`（-1）。事件里不带 `_data.duration`，改带
  `_data.duration_unknown: true`；不能写 0，0 在这里是「解除」。
- **读得更宽**：先把灰条里所有 `txt="…"` 接成一句话再找时长，数字与单位被拆在相邻节点里（`10` + `分钟`）、
  复合写法（`1天2小时`）、`分` / `时` 的简写都认；只看「禁言」之后的部分，昵称里的「3天」不会被当成时长。
- **诊断**：最近一条读不出时长的灰条（去掉了 `uin` 与 `nm`）放进 `internal/status` 的 `inbound.unread_ban_tip`（`POST /v1/internal/status`，要鉴权），
  下次真机上出现，看一眼就知道 QQ 实际写的是什么格式；日志默认静默，所以没往日志里写。

验证：33 项 JVM 测试通过，`NoticesTest` 新增拆节点、复合、简写、昵称干扰、读不出五种情形。
自己发起的禁言（60 秒、10 分钟、1 小时，及解除）在真机上事件里时长与操作者都对，未受影响。
改动在 Java 层，代码内嵌在 Zygisk 的 `.so` 里：装机要覆盖模块文件后**重启手机**才生效。
