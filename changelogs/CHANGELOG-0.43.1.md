# 0.43.1 — 快速撤回不再漏掉原文

群消息刚显示、用户马上撤回时，事件可能这么到：撤回通知先到，原消息的 `message-created` 后到（甚至因为进程重启、本地记录还没落库而暂时查不到）。旧实现只在 `MsgStore` 里查一次原文，查不到就拿回调里的序号凑一个公开 ID 发出去，防撤回那边既找不到原文，也没法再把后到的原消息对回这条撤回。

这一版把撤回投递改成「先确保原消息已登记、已投递，再发撤回事件」，两条入口合成一条路径：

- 内核回调 `onMsgRecall(chatType, peerUid, msgSeq)` 与灰条记录（`grayTipElement.revokeElement`）都走同一套恢复：按 `msgId` 或精确 `msgSeq` 查 `MsgStore`，差一个 emit 就先让常规回调投递。
- 查不到时按 120 / 350 / 800 / 1600 / 3000 毫秒退避，中间从本地 NT 历史（`fetchRecord` / `getHistory`）把原记录找回来，自己先投 `message-created`，随后才发删除事件，客户端的因果顺序仍然正确。
- 恢复窗口结束仍找不到原文才会发撤回事件：只有这时才用序号兜底，绝不提前往 `MsgStore` 写一个假映射污染后续身份。
- 同一撤回的回调与灰条共享一个待处理集合，不会重复投递；`Events` 原有的按消息号去重照旧兜底。

灰条记录的 `msgId` 是灰条自己那条系统记录，不是被撤消息的号。`Convert` 不再用它补 `qq_msg_id`，改由 `revokeElement` 里的原消息号（或留空等恢复）决定；私聊撤回通知补上 `peer_id`，`Codec` 读取时也认这个字段。

新增 `RecallNoticeTest` 覆盖两件事：灰条没有带原号时不得冒用灰条自己的 ID，带了原号时必须是那个公开号。
